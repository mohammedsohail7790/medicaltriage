# Integration and data-handoff specification

Generated by `pnpm evidence:generate` from `src/services/integrationSpecs.ts` and the integration registry. It covers every integration the application can run today: what is exchanged, how, how often, what happens on error and who is responsible (NFR-054, NFR-155). Whether each is configured and live in a deployment is shown in Admin, Integrations, Registry; an integration is live only when it is fully configured and explicitly set live.

A handoff that Qatar Airways agrees in addition to these is added as a new entry, with its fields, mapping, frequency, error handling and owners, before it is switched live. The older `docs/integration-connectivity-touchpoints.md` lists network addresses and sizes for firewall rules; this document is the current specification.

## Qatar Health Information Exchange (`qhie`)

Check a patient's consent and read exchange data before a note is written back.

| | |
|---|---|
| Direction | outbound |
| Protocol | HTTPS, FHIR R4 JSON |
| Authentication | Bearer token (QHIE_ACCESS_TOKEN) |
| When it runs | One consent check per EMR write-back. |
| Data exchanged | Patient identifier (Qatar ID); Consent resource query |
| Kinds of data | personal |
| Mapping | Patient identifier to the FHIR Consent search parameter; the result decides whether the write-back proceeds. |
| Settings it needs | `QHIE_BASE_URL`, `QHIE_ACCESS_TOKEN` |
| Errors and retries | Calls go through the shared outbound client: a failure on the network or a 5xx is retried with doubling back-off (INTEGRATION_<NAME>_RETRIES, default 3), a 4xx never is, and a full queue refuses with 503. Every call is in the interface log with its correlation id. A denied or unavailable consent stops the write-back and the nurse copies the note instead. |
| IRISSTAR is responsible for | The client, retries, logging and fallback. |
| The customer is responsible for | The endpoint, credentials, consent model and availability. |
| Status | Built. Live endpoint and credentials depend on Qatar Airways. |

## EMR (FHIR write-back) (`emr-fhir`)

Write the completed note to the hospital record.

| | |
|---|---|
| Direction | outbound |
| Protocol | HTTPS, FHIR R4 DocumentReference (Cerner Millennium or Epic) |
| Authentication | Bearer token (FHIR_ACCESS_TOKEN or per-destination token) |
| When it runs | Once per completed case, on the nurse's request or queued (EMR_WRITEBACK_ASYNC). |
| Data exchanged | Patient identifier; Practitioner identifier; SBAR note (text, base64); LOINC document type |
| Kinds of data | personal, clinical |
| Mapping | The compiled note becomes a DocumentReference attachment; patient and practitioner map to the subject and author references. |
| Settings it needs | `FHIR_BASE_URL`, `FHIR_ACCESS_TOKEN` |
| Errors and retries | Calls go through the shared outbound client: a failure on the network or a 5xx is retried with doubling back-off (INTEGRATION_<NAME>_RETRIES, default 3), a 4xx never is, and a full queue refuses with 503. Every call is in the interface log with its correlation id. A queued write-back retries up to its limit, then moves to the dead-letter list for replay; the note stays in the encounter. |
| IRISSTAR is responsible for | The mapping, queue, retries and replay. |
| The customer is responsible for | The FHIR endpoint, credentials, profiles and acceptance of the document type. |
| Status | Built and tested against stubs. Live endpoints depend on Qatar Airways. |

## Archive system (`archive-handoff`)

Hand archived records to the designated archive system before local content is removed.

| | |
|---|---|
| Direction | outbound |
| Protocol | HTTPS, signed JSON |
| Authentication | HMAC signature (ARCHIVE_HANDOFF_SECRET) |
| When it runs | Per retention run, per archived record. |
| Data exchanged | The archived record, decrypted; Record type and reference; Content hash |
| Kinds of data | personal, clinical |
| Mapping | Record as stored, with its type and hash; the archive confirms receipt by hash. |
| Settings it needs | `ARCHIVE_HANDOFF_URL`, `ARCHIVE_HANDOFF_SECRET` |
| Errors and retries | A failed handoff keeps the record locally, raises an alert and fails the integrity check after 72 hours; nothing is removed until receipt is confirmed. |
| IRISSTAR is responsible for | Signing, confirmation and the local purge rule. |
| The customer is responsible for | The archive system, its storage and retention. |
| Status | Built. Depends on Qatar Airways' archive system. |
